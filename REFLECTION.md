My pool is a very small version of the idea behind the Linux kernel's kmem_cache. Both keep one cache per object size, cut large blocks of memory (slabs) into equal slots, and hand a slot out or take it back in O(1) by keeping the free-list pointer inside the dead object itself, so a free object costs no extra memory. The differences are mostly things the kernel needs and I do not. kmem_cache_create takes an alignment, flags and a constructor, while pool_create only takes a size. The kernel keeps its slab bookkeeping outside the slab, in the page structure, and it tracks which slabs are full, partial or empty so it can give empty ones back to the page allocator; my pool has one free list across every slab and never gives a slab back until pool_destroy. The kernel also has per-CPU free lists and locking, and mine is single-threaded. Finally, destroying a kmem_cache that still has live objects is treated as a bug, while my pool_destroy allows it and just frees every slab, which leaves any outstanding pointer dangling as the caller's problem. For pool_stats, slabs is the number of 4096-byte slabs the pool has taken from rb_malloc, live is the number of objects handed out by pool_alloc and not yet returned, and free_objs is the number of slots pool_alloc can hand out right now without getting a new slab, which is exactly the length of the free list. I carve a whole slab onto the free list as soon as it is allocated, so there is never a separate group of uncarved slots, and the header bytes and tail padding are not counted. This gives one equation that the tests assert after every operation: slabs * slots_per_slab == live + free_objs. An empty pool reports 0, 0, 0 because pool_create does not allocate a slab. The slab header is in-band: one next pointer at offset 0 of each slab, padded to 16 bytes. I chose this because growing the pool is then a single rb_malloc, so there is one failure point and nothing to unwind when it fails. An out-of-band record would need a second allocation per slab, and if that one failed I would have to free the first. The cost is 16 bytes per slab, which costs my 48-byte tree node nothing, since 4080 / 48 and 4096 / 48 are both 85. For alignment, the slab base comes from rb_malloc so it is aligned for max_align_t, and both the offset to slot 0 and the stride are rounded up to a multiple of 16, so every slot is aligned for a pointer and for anything a caller could store. pool_create is not told an alignment, so this is the one rule that is safe for every caller. The cost is wasted space for small objects (a 17-byte object gets a 32-byte slot). The stride is also at least 8 bytes so the free-list link fits even when the object is 1 byte. I poison dead slots with 0xDD because a use-after-free on a pooled node is invisible to ASan and Valgrind: the slab is still valid memory from malloc, so reading a freed node is not an error to them. With poisoning, a stale read gives obvious garbage, and following a 0xDDDD... pointer crashes right away. pool_free fills the whole slot and then writes the free-list link over the first 8 bytes, because the pool cannot work without the link, so where the two want the same bytes the link wins. That means the first 8 bytes of a dead node are never poisoned. Fresh slots are not poisoned when a slab is carved, so Valgrind still reports them as uninitialized, and pool_alloc does not check that the poison is intact.
