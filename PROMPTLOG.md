7. Mutation 2: pool layout decisions, settled before any allocator code
- Prompt: "where does the intrusive free-list pointer live inside a dead object, and what guarantees its alignment? In-band header or out-of-band, and what does each cost in failure paths? What exactly does free_objs count? How does pool_destroy free slabs while objects are live? Settle all of it, write the three decisions into your devlog with reasons, and then implement only the geometry: one function that computes stride, slots, and offsets, with a unit test that checks the arithmetic directly."
- Decision 1, the free-list pointer lives at offset 0 of the dead slot. A dead object's bytes belong to nobody, so the pool reuses the first sizeof(void *) of them as the link (struct pool_slot { struct pool_slot *next; }). Its alignment is guaranteed by three facts in a chain: rb_malloc returns a slab base aligned for max_align_t (16 here); the offset from the slab base to slot 0 is rounded up to a multiple of 16; the stride is rounded up to a multiple of 16. Every slot address is therefore base + 16k, which is aligned for a pointer and for any object the caller can store. The stride is also at least sizeof(void *), so the link fits when obj_size is 1. Reason for rounding to max_align_t instead of something tighter: pool_create is given a size and no alignment, so this is the one rule that is safe for every caller. Cost: small objects waste space (a 17-byte object gets a 32-byte slot). The 48-byte tree node wastes nothing.
- Decision 2, the slab header is in-band: struct pool_slab { struct pool_slab *next; } at offset 0 of each 4096-byte slab, padded to 16 bytes. Reason: growing the pool is then one rb_malloc, so there is one failure point and nothing has been modified when it fails, which means nothing to unwind. An out-of-band record (a separate list node or an array of slab pointers) needs a second allocation per grow; if the second fails the first has to be freed, which doubles the fault-sweep points and needs goto-cleanup, and a growable array adds a copy step that can fail too. Cost of in-band: 16 bytes per slab. For the node that costs zero slots, since (4096 - 16) / 48 = 85 and 4096 / 48 is also 85.
- Decision 3, free_objs counts the slots pool_alloc can hand out right now without getting a new slab, which is exactly the length of the free list. A new slab has all of its slots pushed onto the free list at once (at most 255 writes, a fixed bound), so there is no separate category of never-used slots. Header bytes and tail padding are not counted. Reason: it gives one equation a test can assert after every operation, slabs * slots_per_slab == live + free_objs. An empty pool reports 0, 0, 0 because pool_create allocates no slab.
- Consequence of decision 2, pool_destroy with live objects: it walks the slab list through the in-band next pointers, saving next before freeing each slab, then frees the pool struct. It never reads the free list or any object, so which slots are live does not matter; their memory goes with the slab. It allocates nothing, so it cannot fail, and it uses O(1) extra space. Two things follow: every outstanding object pointer dangles afterwards (the caller's contract), and a pooled rb_destroy must still walk the nodes first to free keys and values, because those come from rb_malloc and not from the pool.
- What was implemented: pool_geometry(obj_size, &g) in src/pool.c, declared in a new src/pool.h with the five pool prototypes moved there unchanged. It computes first_off = 16, room = 4080, stride = obj_size raised to at least the link size and rounded up to 16, slots = room / stride, link_off = 0. It returns -1 for obj_size 0 or above 4080, checked before rounding so SIZE_MAX cannot overflow, and leaves *g untouched. For the node: stride 48, 85 slots, first_off 16, no tail waste. No pool_create, pool_alloc, pool_free, pool_stats or pool_destroy body exists yet.
- Test: test_pool_geometry in tests/test_rbtree.c. A table of ten hand-computed cases (0, 1, 8, 16, 17, 48, 49, 4080, 4081, SIZE_MAX), then a loop over every obj_size from 1 to 4080 asserting the stride holds the object and the link, the stride and first_off are multiples of 16, the last slot ends inside the slab, and one more slot would not fit.
- Sabotage: in a scratch copy only, slots was changed to POOL_SLAB_SIZE / stride, which forgets the header. Output:
  t: tests/test_rbtree.c:454: test_pool_geometry: Assertion `g.slots == c->slots' failed.
  It fails on the obj_size 1 row (256 slots computed, 255 expected). The 48-byte node row alone would not have caught it, because 4096 / 48 and 4080 / 48 are both 85.
- Limits recorded honestly: (1) The commit before this one (554b502) did not compile. src/pool.c was in the Makefile but held only prototypes with no #include <stddef.h>, so gcc stopped at "unknown type name 'size_t'". Moving the prototypes into src/pool.h fixed it. 9. Mutation 3: teardown and traversal without recursion, and why each method was chosen
- Prompt: "today we are doing the teardown. We will need to reimplement a different rbDestroy and foreach method, but first I want to talk about right-spine rotation or pointer reversal. What is each and why should I choose one over the other"
- What came back: before answering, Claude read src/rbtree.c and pointed at two facts that change the answer: every node has a parent pointer, and rb_foreach takes a const rbtree_t *. It then described both techniques. Right-spine rotation: rotate right at the top until the top node has no left child, free that node, step to its right child. Pointer reversal: keep the way back up inside the tree by temporarily overwriting child pointers and restoring them afterwards, either Schorr-Waite (flip the pointer you descended through, flip it back on the way up, needs a per-node mark) or Morris threading (point the in-order predecessor's empty right pointer at the current node, remove it on the second arrival). It put the choice to me as two questions, one per function, and I took its recommendation on both.
- Decision 1, rb_destroy uses right-spine rotation. Reasons: (1) the tree is being thrown away, so there is nothing to preserve. Pointer reversal spends its extra work putting pointers back, and that work is wasted on nodes that are freed a moment later. (2) It is about ten lines with one local variable. Each rotation is three assignments, and parent and color are not maintained at all. (3) It allocates nothing, so there is no failure path and nothing for the fault sweep to unwind. (4) The node it frees has no left child and its right child is read before the free, so no freed memory is ever read. Cost: O(n) in total, since each rotation moves one node onto the right spine for good. The third option Claude listed, a post-order walk up the parent pointers, would also have met the header; rotation was chosen because it does not depend on the parent field.
- Decision 2, rb_foreach uses neither technique. It starts at the leftmost node and steps to the in-order successor: if there is a right child, go right and then left as far as possible; otherwise climb parent until arriving from a left child. Reasons: (1) both tricks exist to make up for not having a parent pointer, and this tree has one. (2) The walk never writes to the tree, so it honors the const in the header. Morris and Schorr-Waite would both need the const cast away. (3) The tree is a valid red-black tree at every moment the callback runs. Claude's argument against Morris here: a callback that calls rb_find for an absent key lying between the predecessor and the current node would follow the thread back up and loop forever. (4) Right-spine rotation is ruled out for foreach because it destroys the shape. Cost: O(1) space, and O(n) time for the whole walk because each edge is crossed at most twice.
- What was implemented: rb_destroy (75e8be8) with destroy_subtree deleted; the per-node frees are the same as before (value through value_free, key, node unless pooled), then pool_destroy and the tree struct. rb_foreach (2cca6cc) with foreach_subtree deleted. tree_minimum is not reused in rb_foreach because it takes non-const pointers, so the leftmost loop is written inline with const pointers. The climb tests p != nil before reading p->right, so the walk never reads the sentinel's fields, which rb_delete's transplant may have written to. include/rbtree.h was not touched.
- Test: test_foreach_reentrant in tests/test_rbtree.c, run inside the tree battery so it covers plain and pooled trees. It inserts 64 keys in scrambled order and walks them with a callback that, on every visit, checks the key and value are the next in sorted order, calls rb_validate, calls rb_find on the current key, and calls rb_find on the absent keys just above and just below it. No existing test was changed.

- Prompt: "Today we are doing the hostile reviewer. The traversal under the same O(1) constraints, plus the restoration test: keys in order before, rb_foreach, keys in order after, assert they agree. Decide and document what your contract says about a callback that reaches back into the tree."
- What came back: in plan mode, Claude read src/rbtree.c, the tests and episode 9, and said first that the traversal already existed: rb_foreach from 2cca6cc is a parent-pointer walk with no recursion and no writes, so no new traversal code was needed. - Decision, the callback contract: a callback may read the tree it is called from (rb_find, rb_size, rb_validate, a nested rb_foreach) and may change the object its value points to. It may not call rb_insert, rb_delete, rb_destroy or rb_snapshot on that tree; doing so is undefined behaviour and is not detected. Claude made this decision and I approved it with the plan. The contract is a comment above rb_foreach in src/rbtree.c, because include/rbtree.h cannot be changed.
- Reasons given for the contract: (1) Reads are safe because the walk never writes, so the tree is a valid red-black tree every time the callback runs, and a nested walk has its own two local variables. (2) rb_delete breaks the walk three ways: deleting the current key when its node has 0 or 1 children frees the node the walk is standing on; deleting it when it has 2 children swaps the successor's key into that node, so that key is skipped; deleting the in-order predecessor when it has 2 children frees the current node, because our delete frees the successor's node. On a pooled tree ASan would not see the first or third, since the node goes back to the slab. (3) Detection was rejected: it needs a flag written through a const rbtree_t * and a new meaning for -1 from rb_insert and rb_delete, which the header defines as "allocation failure" and "absent". (4) Supporting insert was rejected even though it happens to be memory-safe today: Mutation 4 might not be able to keep the promise, and a callback that keeps inserting larger keys never ends. (5) The safe pattern is in the comment: collect keys in the callback, delete after rb_foreach returns.
- Test: test_foreach_restoration in tests/test_rbtree.c, called in the tree battery right after test_foreach_reentrant, so it runs on plain and pooled trees. It inserts 128 keys in scrambled order and deletes every third, leaving 85. Walk 1 records, per visit, the key pointer, a copy of the key text, and the value pointer, and is checked against the keys the test knows it left in.
