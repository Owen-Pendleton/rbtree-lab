7. Mutation 2: pool layout decisions, settled before any allocator code
- Prompt: "where does the intrusive free-list pointer live inside a dead object, and what guarantees its alignment? In-band header or out-of-band, and what does each cost in failure paths? What exactly does free_objs count? How does pool_destroy free slabs while objects are live? Settle all of it, write the three decisions into your devlog with reasons, and then implement only the geometry: one function that computes stride, slots, and offsets, with a unit test that checks the arithmetic directly."
- Decision 1, the free-list pointer lives at offset 0 of the dead slot. A dead object's bytes belong to nobody, so the pool reuses the first sizeof(void *) of them as the link (struct pool_slot { struct pool_slot *next; }). Its alignment is guaranteed by three facts in a chain: rb_malloc returns a slab base aligned for max_align_t (16 here); the offset from the slab base to slot 0 is rounded up to a multiple of 16; the stride is rounded up to a multiple of 16. Every slot address is therefore base + 16k, which is aligned for a pointer and for any object the caller can store. The stride is also at least sizeof(void *), so the link fits when obj_size is 1. Reason for rounding to max_align_t instead of something tighter: pool_create is given a size and no alignment, so this is the one rule that is safe for every caller. Cost: small objects waste space (a 17-byte object gets a 32-byte slot). The 48-byte tree node wastes nothing.
- Decision 2, the slab header is in-band: struct pool_slab { struct pool_slab *next; } at offset 0 of each 4096-byte slab, padded to 16 bytes. Reason: growing the pool is then one rb_malloc, so there is one failure point and nothing has been modified when it fails, which means nothing to unwind. An out-of-band record (a separate list node or an array of slab pointers) needs a second allocation per grow; if the second fails the first has to be freed, which doubles the fault-sweep points and needs goto-cleanup, and a growable array adds a copy step that can fail too. Cost of in-band: 16 bytes per slab. For the node that costs zero slots, since (4096 - 16) / 48 = 85 and 4096 / 48 is also 85.
- Decision 3, free_objs counts the slots pool_alloc can hand out right now without getting a new slab, which is exactly the length of the free list. A new slab has all of its slots pushed onto the free list at once (at most 255 writes, a fixed bound), so there is no separate category of never-used slots. Header bytes and tail padding are not counted. Reason: it gives one equation a test can assert after every operation, slabs * slots_per_slab == live + free_objs. An empty pool reports 0, 0, 0 because pool_create allocates no slab.
- Consequence of decision 2, pool_destroy with live objects: it walks the slab list through the in-band next pointers, saving next before freeing each slab, then frees the pool struct. It never reads the free list or any object, so which slots are live does not matter; their memory goes with the slab. It allocates nothing, so it cannot fail, and it uses O(1) extra space. Two things follow: every outstanding object pointer dangles afterwards (the caller's contract), and a pooled rb_destroy must still walk the nodes first to free keys and values, because those come from rb_malloc and not from the pool.
- What was implemented: pool_geometry(obj_size, &g) in src/pool.c, declared in a new src/pool.h with the five pool prototypes moved there unchanged. It computes first_off = 16, room = 4080, stride = obj_size raised to at least the link size and rounded up to 16, slots = room / stride, link_off = 0. It returns -1 for obj_size 0 or above 4080, checked before rounding so SIZE_MAX cannot overflow, and leaves *g untouched. For the node: stride 48, 85 slots, first_off 16, no tail waste. No pool_create, pool_alloc, pool_free, pool_stats or pool_destroy body exists yet.
- Test: test_pool_geometry in tests/test_rbtree.c. A table of ten hand-computed cases (0, 1, 8, 16, 17, 48, 49, 4080, 4081, SIZE_MAX), then a loop over every obj_size from 1 to 4080 asserting the stride holds the object and the link, the stride and first_off are multiples of 16, the last slot ends inside the slab, and one more slot would not fit.

  It fails on the obj_size 1 row (256 slots computed, 255 expected). The 48-byte node row alone would not have caught it, because 4096 / 48 and 4080 / 48 are both 85.
